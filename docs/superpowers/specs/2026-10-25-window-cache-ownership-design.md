# Владение кэшем между окнами — дизайн

Дата: 2026-10-25. Запрос пользователя: «описание фичи, которая устранит проблемы с отзывчивостью, неоптимальности и
перепотребление ресурсов в Loupe» — первый из трёх слоёв (слой 1: владение кэшем между окнами; слои 2 «эскизы, обложки,
листинги» и 3 «память под давлением» — отдельными спеками следом). Основание — исследование `spikes/rust/REPORT.md`
и его материалы (`spikes/rust/reports/window-switch-map.md`, `memory-audit.md`, `bench-results.md`). Решения A/A/A/A
по четырём вопросам выбраны пользователем.

## Цель

Loupe с несколькими окнами (вкладками) на медленных шарах остаётся отзывчивым: переключение окон не выбрасывает работу
другого окна, восстановление сессии не блокирует интерфейс и не гоняет шару N раз, возврат в окно показывает картинку
сразу и ничего не перечитывает, память после закрытия окон возвращается на плато.

Проверяется бенчами (`scripts/session-bench.py`, `scripts/switch-bench.py`, `LoupeBench replay --script close`) на M4 и на
Intel с NAS-папками: ноль проб главного потока > 100 мс на M4 и известная цифра на Intel; `other windows −N` = 0 при
бюджете, вмещающем keep set'ы; `rereads` = 0 при возврате в окно; ровно одна активация при restore; footprint после
закрытия окон на плато.

## Что измерено сейчас (M4 Max, 36 ГБ, 5 full-screen окон с 147-МП JXL из Last Session, ПК-шара по Ethernet)

- За 30 с переключений: 63 вытеснения записей других окон, 11 ГБ выброшенной работы (`other windows −63 (11027 MB)`);
  при возврате окно начинает с `state=bytes` — пирамиды нет.
- Главный поток не зависал > 250 мс; переключение Space 480–650 мс — системная анимация.
- `LoupeBench replay` 30 × 108 МП при бюджете 4 ГиБ: пик 5,7 ГБ, после опустошения плейлиста остаётся 4,5 ГБ
  (GPU 4,26 ГБ).
- Механизмы по коду: `CacheOwners.protected` защищает только текущую фотографию (`CacheOwners.swift:45-53`);
  `setActivity` → `reconcile` отменяет ожидающие задания предыдущего окна и чтения без заданий (`ImageCache.swift:340-368`),
  stamp-check нового окна идёт с `isCurrent` и паузит все чужие чтения (`IOPool.yieldToCurrent`);
  `WindowRegistry.open(session:)` строит все окна в одном обороте и вызывает `bringToFront` у каждого
  (`WindowRegistry.swift:319-336`); `unregister` ничего не освобождает (`ImageCache+Sessions.swift:30-35`).

## 1. Защищённое соседство (keep set)

- У каждой зарегистрированной сессии есть **keep set**: текущая фотография (и вторая страница разворота) на уровне,
  который ей нужен (`ShowPolicy` по зуму и экрану), плюс по одному соседу с каждой стороны на уровне превью.
- `CacheOwners.keepSets(sessions:, budget:, estimate:) -> [CacheSessionID: [URL: CacheGoal]]` заменяет `protected`.
  Оценка размера — те же факты, что у `CachePlan.estimatedSize`. Если сумма оценок превышает `keep-share` бюджета
  (новый ключ `loupe.conf`, доля `cache-memory`, по умолчанию 50 %, диапазон 0–80 %), усечение идёт в порядке «дольше
  всех неактивная сессия — первой»: сначала снимаются соседи, потом текущая фотография понижается до превью; активная
  сессия усекается последней и никогда ниже сегодняшней защиты (её текущая фотография на нужном уровне).
- `evictionOrder` получает keep set'ы и не возвращает их URL; остальной порядок — как сейчас (ничьи → неактивные по
  давности → активная, дальние первыми).
- Под давлением памяти (`pressure`) `keep-share` делится вместе с лимитом (÷2, ÷4), keep set'ы усекаются тем же
  правилом — они не обходятся.
- План неактивной сессии равен её keep set'у (вместо `shortPlan` «одна фотография для видимых») и исполняется в классе
  `.keep` (§2). План активной сессии не меняется.
- `CacheStats` получает `keptForOtherWindows` (байт) рядом с `evictedInactive`; Diagnostics показывает его в строке
  `Cache use` (`· kept for other windows N MB`).

## 2. Переключение окон

- Классы заданий: `.foreground` (план активной сессии, как сегодня) и `.keep` (keep set'ы остальных). `reconcile`
  строит `wants` из обоих. Задание предыдущего окна, попавшее в `.keep`, не отменяется, а переводится в этот класс:
  чтение остаётся в очереди `IOPool` ниже чтений активной сессии и выше эскизов; декод — в обычных слотах `DecodePool`
  без резервированного. Задание вне keep set отменяется, как сегодня.
- Классы чтений: `IOJob.isBackground` расширяется до `enum ReadClass { case current, foreground, keep, background }`.
  `yieldToCurrent` приостанавливает только `.foreground` и `.background`; `.keep` продолжается (не больше одного чтения
  на окно: текущая фотография или сосед).
- Доведение чтения: `FileReader` отменяет чтение, только если прочитано меньше `finishReadAbove` файла (константа,
  стартово 0,5; значение подтверждается замером на NAS в bench-документе). Иначе чтение доводится, байты кладутся в
  запись как `.bytes` с владельцем-сессией и подчиняются обычному порядку вытеснения. Прогресс берётся из учёта
  bytes-in-flight, который уже ведёт watchdog `IOPool`.
- Stamp-check при активации: первым в очереди (`priority.isCurrent`), но если запись текущей фотографии уже на нужном
  уровне (пирамида цела), он ставится в `.foreground`, а не `.current` — картинка уже на экране, пауза чужих чтений
  ради `stat` не нужна. Свежесть штампа проверяется как сейчас.
- `CacheStats.rereads`: число повторных чтений одного URL с носителя за время жизни процесса (чтение URL, чьи байты уже
  были в кэше и были вытеснены). Печатается в `activate`-строке лога рядом с `other windows`.

## 3. Восстановление сессии

- `WindowRegistry.open(session:)` строит фронтальное окно (selected window, его selected tab) сразу: `makeController` +
  `restore` + `bringToFront` — единственная активация при restore. Остальные окна — очередь `pendingWindows`, по одному
  в `DispatchQueue.main.async` после показа предыдущего: `showWindow` + `restore(step)` без `bringToFront`/`makeKey`;
  порядок Z — `window.order(.below, relativeTo:)` относительно предыдущего построенного. Вкладки: только selected
  строится, остальные `.lazy`, как сейчас.
- `HomeGrid.availability` остаётся для `.home`-замены пропавших путей, но фронтальное окно его не ждёт (таймаут 0 для
  его пути: не ответил — открывается как `.open`, ошибку покажет обычный путь загрузки); остальные окна ждут результат
  не дольше 1 с, параллельно с построением фронтального.
- Фоновые окна регистрируются `setActivity(active: false, visible: false)`: их план — keep set в классе `.keep` (§1–2),
  первый показ — эскиз из каталога (stand-in), как сегодня при `jump preview`.
- Листинги фоновых окон (`Playlist.relist`, `quickList`) откладываются до первой активации окна или до завершения
  листинга активного окна (событие `folder names` активной сессии; без таймера). `FolderWatcher` фоновых окон остаётся
  на паузе по невидимости.
- `enterFullScreenInTurn` — как сейчас, фронтальное окно первым; удержание показа фото (до 3 с) только у него.
- `applicationDidBecomeActive` → `forgetFolderListings()` не меняется (слой 2).

## 4. Закрытие окна

- `unregister` освобождает сразу: отменяет задания сессии в обоих классах и её чтения (без доведения); для каждой
  записи, которую не листит ни одна оставшаяся сессия, — `dropPyramid` + `degrade(.bytes)`; записи, которые листит
  другая сессия, остаются под её keep set'ом/планом. Затем `malloc_zone_pressure_relief`, как после `trimIdle`.
- `ViewerView.teardown()` обнуляет `shownImage` и страницы-снапшоты `RenderLoop` при закрытии (сейчас только
  останавливает линки), иначе GPU-текстуры живут до деаллокации контроллера. Деаллокация `ViewerWindowController`
  подтверждается разрушающим тестом (лог «viewer window freed» есть).
- «Открыть закрытую вкладку» — обычное открытие, один декод; ради неё ничего не кэшируется.
- `LoupeBench replay --script close`: open → pan → close × 20, footprint после каждого цикла; критерий плато —
  последние 10 циклов в пределах ±5 % и не выше суммы keep set'ов оставшихся окон плюс базовый уровень процесса.

## 5. Проверка и граница объёма

- Бенчи до/после (CLAUDE.md): `spikes/rust/bench/session-bench.py` и `switch-bench.py` переезжают в `scripts/` и
  читают из лога `other windows −N`, `rereads`, `keptForOtherWindows`, число активаций при restore, число
  одновременных листингов. Прогон на M4 и на Intel с NAS-папками; таблица до/после в
  `docs/bench/<дата>-window-ownership.md`, цена каждой из четырёх правок отдельно (одна правка — один замер).
- Тесты (Swift Testing): `CacheOwnersTests` — 5 сессий × 147 МП при 4 ГиБ: keep set'ы целы; при 1 ГиБ: соседи сняты у
  трёх самых старых, текущие целы; `evictionOrder` никогда не возвращает URL из keep set. `ImageCacheTests` — классы
  заданий при `setActivity`, доведение чтения ≥ `finishReadAbove`, stamp-check без паузы `.keep`, `unregister`
  освобождает всё ничьё. `SessionRestorePlanTests`/`WindowRegistry` — порядок построения, одна активация.
  `IOPoolTests` — классы чтений и `yieldToCurrent`.
- Без feature flag: старое поведение не сохраняется как fallback, откат — git. Каждая из четырёх правок — отдельный
  коммит с замером.
- Не входит: гейт генератора эскизов/обложек на `.idle`, перечитывание папок при активации приложения, баг «шара
  недоступна», осцилляция лимита под давлением через 30 с, `ThumbnailCells` по байтам (слои 2 и 3).
- Настройки: только `keep-share`. `finishReadAbove` — константа с замером.
