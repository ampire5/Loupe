# Work that grows with the folder

An audit of the paths that grow with the folder (owner, 2026-10-28: "potential non-optimal algorithms"), measured with
`LoupeBench hotpaths` on a synthetic folder of 50 000 photos (a big NAS folder), half their sizes and aspects known;
no disk. Median of 9 runs after a warm-up, release build, M4 Max (Apple silicon), macOS 27. Profiles with `sample`
on `LoupeBench hotpaths --only <name> --runs 40`.

| path | thread | before, ms | after, ms | what it cost |
|---|---|---|---|---|
| folder open (`FolderRequest.playlist`, date-desc, remembered photo) | main | 1348 | 234 | the playlist built three times (the third in the name order: a bug, the folder's sort lost on a remembered photo); `BrowserSort.order` moving the large `BrowserEntry` through generic code; `standardizedFileURL` three passes |
| folder re-read (`ViewerSession.apply`: sort, replace, compare) | main | 188 | 37 | the sort (78 % of the profile), then the standardizing |
| strip aspects on a fetch batch (every 250 ms of a generation pass) | main | 5.2 | 0.005 | all the aspects made again for a batch of a few |
| strip aspects: "every unknown" filter | main | 6.3 | 4.5 | kept: only at the playlist's first fetch and its first cell picture |
| strip layout (`FilmstripLayout` and its compare) | main | 0.013 | — | nothing to do |
| Home grid index per visible-range request | main | 5.3 | 0 (4.8 once per listing) | the index made again for every request, the cards counted over every entry |
| cache plan per reconcile | cache actor | 5.9 | 0.10 | the size estimate looked up every photo of the folder |
| zoom rules from a folder's values | main | 0.001 | — | nothing to do |

## The fixes

- `FolderRequest.playlist` builds the playlist once in the folder's sort and moves to the remembered photo
  (`Playlist.move(to:)`) instead of building it again in the name order.
- HomeScreenKit `BrowserSort.order` finds the order on small keys (index, leads, is-file, the value) and moves the
  entries once; the same order (`theOrderOnKeysIsTheEntriesOrder`).
- HomeScreenKit `URL.quicklyStandardized`: a listing's absolute file URL without `.`, `..`, empty components and not
  under `/private` is kept as it is (standardizing drops `/private` from a path that exists without it); 14 ms against
  55 ms for 50 000 URLs.

- `StripAspects` keeps each file's index and changes only the arrivals' places in `aspects`.
- Home (`FolderBrowserSource`) keeps the shown files' index until they change, and counts the cards when it
  remembers the entries.
- `CachePlan`'s size estimate is the median of the known sizes within `CachePlan.estimateReach` (500) of the
  current photo: the neighbours are probed first and come from the same shoot.

Intel: not measured (no Intel Mac at hand); expect 3–5× these times.

## Folder preparation off main (2026-10-29)

The remaining folder-open cost above was still paid on the main actor after the asynchronous listing returned.
`ViewerSession.openFolder`, `openFolderStripTarget` and `goFolder` now await one process-wide
`FolderPlaylistPreparation` actor: URL normalization, filtering, stamp copying, sorting and remembered-file lookup
run serially outside main. These user-awaited tasks use `.userInitiated` priority. The final main-actor commit
checks cancellation, the request token and whether the target is still wanted. Closing a session cancels its open;
a superseded strip request does not call a completion that could cancel the newer interaction. An unwanted current
selection clears its loading message; photo navigation cancels preparation too.

Reproduce with `LoupeBench hotpaths --only folder --runs 9` (release, same synthetic 50 000-file case).
Three consecutive rounds on MacBook Pro Mac16,6, M4 Max (14 physical cores), 36 GB, macOS 27.0.1.
Each round warms up once. CPU is `CLOCK_THREAD_CPUTIME_ID` on the real main thread; the asynchronous measurement
keeps its run loop running while it awaits exactly the same preparation actor as the viewer.

| preparation | round 1 | round 2 | round 3 |
|---|---:|---:|---:|
| synchronous baseline: main CPU, ms | 268.289 | 262.691 | 237.984 |
| asynchronous preparation: main CPU, ms | 0.030 | 0.026 | 0.028 |
| asynchronous preparation: wall time, ms | 276.614 | 234.996 | 249.521 |

`sample` on `hotpaths --only 'folder open' --runs 40` confirms `FolderRequest.playlist` / `Playlist.init` and
`FolderPlaylist` / `BrowserSort` on the main thread before the change. With `--only 'folder prepare' --runs 40`,
preparation is on `com.apple.root.user-initiated-qos.cooperative` and main waits in its run loop
(`mach_msg2_trap`); that profiled run measured 258.157 ms wall / 0.028 ms main CPU. The worker serializes preparation across
windows instead of starting a sort on every core. Cancellation is checked before building and after sorting;
a sort already running finishes its synchronous pass, but its cancelled result is discarded.

This measures preparation and the actor hop, including the main run loop's CPU while waiting; it excludes listing,
`ViewerSession`'s subsequent cache/strip/UI updates and the folder re-read path (still measured separately).
Intel hardware and the complete window action have not been measured.
